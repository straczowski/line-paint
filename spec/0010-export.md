# 0010 Export

## What

A person can download the drawing as SVG or as GCode. Both files are built from the same written points.

A menu button sits at the top left. It is an icon button, `RiMenuLine`, on a white island, with the island shadow and radius from DESIGN.md. The button is `2rem`, the icon `1rem`, with `aria-label="Menu"`. It toggles a menu. The menu holds Export GCode, then Export SVG. Each action is a quiet text button, not a primary button. Choosing an action downloads the file and closes the menu. Export is not painted on the canvas.

One pure function in `src/scene/` builds the written points. Two more turn those points into the file strings. The menu writes a string to a file. The scene is unchanged.

A polyline is left out when any stored point lies outside the sheet. Outside means `x < 0`, `x > 297`, `y < 0`, or `y > 210`. A point on the edge stays in. The omitted polyline is not clipped, and it is not deleted from the scene. Polylines that remain stay in scene order.

The written points of a kept polyline are its stored points. When `closed` is true, that list appends the first point again. The list does not flip Y. Nothing scales, pads, or recenters the points.

Export SVG downloads `drawing.svg`. The document matches the shape of line-weaver's `generateSvgDocument`, at sheet size:

`<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 297 210" width="297" height="210" style="background: white">`

An empty written set is that open tag and `</svg>`, with no path. Otherwise there is one path per written list and no other geometry. Each path matches line-weaver's `convertPolylineToPath`: `M x,y` then `L x,y`, commands separated by a space, coordinates separated by a comma. Attributes follow line-weaver's path element: `stroke` from the element, `stroke-width` from its width, `stroke-linecap="round"`, `stroke-linejoin="round"`, `fill="none"`. A coordinate is rounded to hundredths of a millimeter, and a whole number is written without a fraction. The SVG writer applies `210 - y` before that rounding, so scene `(0, 0)` is the bottom-left of the file and scene `(297, 210)` is the top-right.

Export GCode downloads `drawing.gcode`. The commands match line-weaver's `convertToGcodeCommands`, without its comment. The constants are pen up `M5`, pen down `M3 S1000`, pause `G4 P0.5`, and feed `G1 F3000`. The file starts with pen up, pause, pen down, pause, pen up, pause, feed. Then each written list is `G0` to the first point, pen down, pause, `G1` through the remaining points, pen up, pause. The file ends with `G0 X0 Y0`. Coordinates are the written scene numbers, rounded the same way as the SVG numbers. An empty written set is that preamble and the return to origin, and no other moves.

## Out of scope

- A preferences panel. The four command strings are constants.
- Import SVG. It is on the Later list.
- A stroke-color control, a width control, and fill.
- Travel reorder, merging polylines, grouping, and a second file name.
- Scaling, padding, recentering, and flipping X.
- Portrait.
- Zod. The app writes strings. It does not parse them.
- The comment `; Generated by Line Weaver`.

## Pitfalls

CONCEPT.md says two export buttons. DESIGN.md puts export in the top-left menu, not on the canvas. The menu is that placement. DESIGN.md also names preferences in that menu and does not define one. A settings form here would be a feature with no spec.

Line-weaver's `generateSvg` is one document and one path per polyline. Its viewBox is the image size, and its stroke width is a pixel setting, often 3. Copying either would scale a drawing that is already millimeters. The document size is the sheet. The path uses the element's stroke and `widthMm`.

Line-weaver's SVG coordinates are already Y-down. This scene is Y-up. ARCHITECTURE.md says `src/render/` flips Y for the canvas, and landscape GCode copies the scene numbers. The SVG writer is the other place that applies `sceneYToTop`. The written-point function must not, because GCode reuses that list.

Line-weaver's `generateGcode` scales, flips X, merges, and reorders before `convertToGcodeCommands`. Its sheet target is 297 by 211 with 40 mm of padding. CONCEPT.md forbids the scale, the pad, and the recenter, and says landscape GCode uses the millimeter numbers unchanged. The reorder is allowed later and is not this file. The X flip would send the pen to the other side of the bed. The format this spec copies is `convertToGcodeCommands`, not that pipeline.

`convertToGcodeCommands` begins with `; Generated by Line Weaver` and an opening pen cycle, and ends with `G0 X0 Y0`. The comment names the other app, so it stays out. The pen cycle and the return to origin are the machine format, so they stay. They are not a preferences form.

The sheet test uses the stored points, before the closing point is appended. Appending by mutating the element would show a duplicate handle in point editing.

A polyline with one point outside is omitted as a whole. Clipping it to the sheet edge would invent a point the person did not draw.

Round caps and joins are fixed. They are not controls.

## Done when

- The top-left menu contains Export GCode and Export SVG. They download `drawing.gcode` and `drawing.svg`. The scene is unchanged.
- A polyline with any stored point outside the sheet is absent from both files. A point on the sheet edge is kept. The scene still contains the omitted polyline.
- The SVG is 297 by 210, with line-weaver's path syntax, `fill="none"`, and the element's stroke and width. Scene `(0, 0)` is the bottom-left of the file. Scene `(297, 210)` is the top-right.
- The GCode file uses the pen cycle, feed, `G0` / `G1` motion, and `G0 X0 Y0` from `convertToGcodeCommands`. Scene `(10, 20)` is `X10 Y20`.
- A closed polyline repeats its first point in both files. An open one does not. Scene points do not change.
- Neither file scales, pads, recenters, or flips X.
- Tests cover the sheet omission, the document size, the Y map, the closing point, the GCode motion, and the absence of scale or padding. `npm test` and `npm run build` succeed.
